# Mosaic リポジトリ Wiki の編集方針

- 本文・見出し・要約を日本語で記述する。識別子、パス、コマンドは原文を保つ。
- この Wiki は現在のコードとテストを調べるための案内・説明である。ユーザー仕様は `docs/spec.md` と `docs/spec/`、設計は `docs/architecture/`、判断履歴は `docs/adr/`、作業手順は `AGENTS.md` と `docs/development-workflow.md` を正本とする。
- 正本を全文複製せず、責務・処理の流れ・境界・変更時の調査先を説明し、関連する正本、実装、テストへ相対リンクを付ける。
- `settings.gradle.kts` に登録された各 Gradle module に個別の説明ページを持たせる。feature の Domain / Data / UI、app の executable / composition / presentation、core、開発ツールもそれぞれ対象とし、`modules/` 配下に配置する。人間がソースコードを読む前に理解できるよう、「概要と主要な責務 → 主要な概念 → 主要な構成要素と役割 → モジュール内部の関係 → 他モジュールとの関係」の順に説明する。詳細は以下の生成要件に従う。
- module の追加・削除・移動時には説明ページと quickstart の案内も更新する。個別ページから関連 module と既存の横断的な architecture / workflow ページへリンクし、全体像と詳細を往復できるようにする。
- 実装と文書が食い違う場合は、両方の根拠を示す。コードだけを理由に仕様・設計を確定しない。
- 重要な振る舞い、所有権、依存方向、永続化、失敗時の扱いには現在のリポジトリ内の根拠を記録する。
- 設定値・スキーマ番号などは必要なときだけ記載し、変更されやすい数値や全シンボルの一覧を重複管理しない。
- リポジトリの Knowledge 機能と、この開発用 OpenWiki を区別して説明する。
- 認証情報、実ユーザーデータ、ローカル環境の絶対パス、生成ログ、ビルド成果物を Wiki に含めない。
- 更新は Codex の OpenWiki 連携から行う。OpenWiki 用の GitHub Actions workflow は不要であり、無効化した雛形もリポジトリに残さない。生成ツールが `.github/workflows/openwiki-update.yml` や定期更新を前提とする案内を再作成した場合は、生成完了後に取り除く。

## モジュール説明ページの生成要件

### 目的と調査方針

- 人間が「このモジュールは何を担い、どのような概念や構成要素が、どう協調して責務を実現するのか」を理解するための解説を生成する。ファイル一覧や API リファレンスの機械的な複製を目的にしない。
- 代表的な入口だけでなく、対象 module の production source 全体と、重要な呼び出し元・具体実装・テストを調査する。広く調査することと、調査した宣言をすべて文章に載せることは区別する。
- 生成 AI は実在する宣言、利用関係、現在の設計・仕様を根拠に意味を解釈し、重要な情報を選んで要約する。ディレクトリ名・クラス名だけで役割や設計意図を断定しない。未確認の関係を推測で補わない。
- 構成要素の選択はモジュールの理解への寄与を基準とする。公開 API、private helper、メソッドを一律に列挙せず、中核的な公開契約、役割を持つ型、処理を支える実装、責務の接続点を説明する。
- 実装と設計文書が食い違う場合は両方の根拠を示し、実装のみを理由に仕様や設計を確定しない。

### ページの構成

説明は次の順序を基本とする。小規模な module は節を統合してよい。大規模な module は責務別に分けてよいが、概要から詳細へ進む流れを維持する。

1. **概要と主要な責務**
   - 何のための module で、何を実現・所有し、どこまでを担当するかを平易な文章で説明する。Domain / Data / UI、app、core などの位置づけは必要に応じて示す。
   - 他の Context が所有するものとの違いなど、境界を理解するために重要な対象外の責務も簡潔に示す。Gradle module と Domain Context を安易に同一視しない。
2. **主要な概念**
   - コードの型名に先立って、扱う情報、状態、業務上・技術上の概念を説明する。概念が複数の型にまたがる場合や、単一の型に対応しない場合もそのまま説明する。
   - 概念同士の違いと、それぞれが必要な理由を優先する。細かなデータ項目を列挙する必要はない。
3. **主要な構成要素と役割**
   - class、interface、object、data class、sealed 型、enum、typealias、トップレベル関数・拡張関数などから、理解に重要な登場人物を選ぶ。概念との対応、責務、所在へのソースリンクを示す。
   - 型名やファイル名を並べるだけでなく、「何を受け持つのか」「他の構成要素との違いは何か」を説明する。役割別にまとめ、必要なら短い表を使う。
   - 重要な公開契約・主要実装は漏らさず、補助的な型やメソッドは役割が伝わる単位にまとめる。主要なメソッドの入力・出力・副作用は理解に必要な場合に限り取り上げる。
4. **モジュール内部の関係**
   - 紹介した構成要素が互いにどう協調して責務を実現するかを説明する。呼び出し、委譲、interface と実装、状態の所有と受け渡し、生成・注入など重要な関係を優先する。
   - 代表的な処理の流れは関係の理解に役立つ場合に取り上げる。重要な状態遷移や失敗時の振る舞いも、理解に必要な範囲で組み込む。入口から全メソッドを順に追跡する義務は設けない。
5. **他モジュールとの関係**
   - この module を利用する側、依存する module、やり取りする公開契約、責務やデータ所有の境界を整理する。単に Gradle dependency を列挙せず、何のために連携するのかを説明する。
   - 具体実装が別 module にある場合は、確認できる実装先と composition の接続点を示す。関連 module ページや正本へのリンクを付ける。

ページ末尾には、主要な実装、関連テスト、仕様・アーキテクチャ、関連 module への導線を簡潔に置く。変更時の注意や詳細なエラー処理は、モジュール理解に重要な場合だけ補足する。

### 読みやすい文章の要件

- 人間が初めて読むことを前提に、まず概念と役割を自然な日本語で説明し、その後に必要な識別子を紹介する。識別子を理解の前提として突然登場させない。
- 一文に多くの関係や操作を詰め込まない。「誰が」「何を」「なぜ」「どのように」「どうなる」を読み取れる文章にする。短すぎる断片をつなぐだけの箇条書きにも偏らない。
- 型名・関数名・略語・矢印記号を連結した圧縮表現や、宣言名を大量に並べる説明を避ける。必要な専門用語は初出で意味と役割を伝え、同じ概念には一貫した呼び方を使う。
- 単なる「呼び出す」「委譲する」だけで終わらせず、その連携によって何が実現されるのかを説明する。ただし実装から確認できない「なぜ」は創作しない。
- 表は構成要素の比較や役割の整理に使い、複数の責務や API を一つのセルに詰め込まない。図による補足は以下の Mermaid 図の利用方針に従う。
- 読者の理解に直接関係しない設定値・スキーマ番号、例外の枝葉、テストの細目は説明の中心に置かない。具体例が理解を助ける場合は、実装で確認できる短い例を使う。
- 人間が読んだときに「何をする module か」「どの登場人物が何を担うか」「それらがどう連携するか」「他の module とどう接続するか」を自分の言葉で説明できることを目標とする。

### Mermaid 図による説明の補足

- 構成要素の関係や処理の流れが文章だけでは把握しにくい場合は、Mermaid 図を積極的に使って理解を助ける。図は本文の補足であり、図だけで説明を完結させない。単純な関係まで無理に図示する必要はない。
- モジュール内部の構成要素の依存・実装・委譲には `flowchart` や `classDiagram`、モジュール間の協調やデータの流れには `flowchart`、代表的な呼び出し順・結果の受け渡し・主要な失敗経路には `sequenceDiagram`、状態の変化には `stateDiagram-v2` など、目的に合う図を選ぶ。
- 一つの図では一つの主題を示し、主要な登場人物と理解に必要なつながりだけを残す。詳細な関数呼び出しやすべての分岐を詰め込まず、必要なら図を分ける。
- 図の前後に、何を示しているか、その関係がモジュールの責務にどう寄与するかを自然な日本語で説明する。図のラベルも簡潔で意味が分かる表現にし、ソースの識別子を使う場合は本文で役割を導入する。
- 図示する依存・呼び出し・状態遷移・処理順序は、現在のソースコード、テスト、正本文書で確認できたものに限る。推測による接続や、実装と異なる単純化を避ける。説明のために一部を省略する場合は、必要に応じて模式図であることと省略範囲を示す。
- Mermaid の構文が正しく、図の方向や矢印の意味に矛盾がなく、表示時にも読みやすいかを生成後に確認する。図中で根拠へのリンクを大量に埋め込むのではなく、対応するソースや関連文書へのリンクを本文から示す。

### 生成後の確認

- 概念・構成要素・内部関係・モジュール間の関係の順で説明され、重要な役割や接続が抜けていないか、調査したソースと照合する。
- 文章が識別子の一覧や API 呼び出しの羅列に偏っていないか、専門用語を知らない読者が順番に理解できるかを見直す。冗長な API 詳細は削り、理解に必要な因果関係は補う。
- 重要な主張の根拠とソース・テストへのリンクを維持する。未確認事項は未確認と明記し、ソースコードから一意に決まる情報を重複管理しない。
