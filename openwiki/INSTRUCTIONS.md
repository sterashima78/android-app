# Mosaic リポジトリ Wiki の編集方針

- 本文・見出し・要約を日本語で記述する。識別子、パス、コマンドは原文を保つ。
- この Wiki は現在のコードとテストを調べるための案内・説明である。ユーザー仕様は `docs/spec.md` と `docs/spec/`、設計は `docs/architecture/`、判断履歴は `docs/adr/`、作業手順は `AGENTS.md` と `docs/development-workflow.md` を正本とする。
- 正本を全文複製せず、責務・処理の流れ・境界・変更時の調査先を説明し、関連する正本、実装、テストへ相対リンクを付ける。
- `settings.gradle.kts` に登録された各 Gradle module に個別の説明ページを持たせる。feature の Domain / Data / UI、app の executable / composition / presentation、core、開発ツールもそれぞれ対象とし、`modules/` 配下に配置する。単なるディレクトリやシンボルの一覧ではなく、その module の責務、主要な構成要素とその関係、代表的な API と処理の流れ、依存先との境界、所有する状態と失敗時の扱い、変更時に確認する実装・テストを説明する。詳細は以下の生成要件に従う。
- module の追加・削除・移動時には説明ページと quickstart の案内も更新する。個別ページから関連 module と既存の横断的な architecture / workflow ページへリンクし、全体像と詳細を往復できるようにする。
- 実装と文書が食い違う場合は、両方の根拠を示す。コードだけを理由に仕様・設計を確定しない。
- 重要な振る舞い、所有権、依存方向、永続化、失敗時の扱いには現在のリポジトリ内の根拠を記録する。
- 設定値・スキーマ番号などは必要なときだけ記載し、変更されやすい数値や全シンボルの一覧を重複管理しない。
- リポジトリの Knowledge 機能と、この開発用 OpenWiki を区別して説明する。
- 認証情報、実ユーザーデータ、ローカル環境の絶対パス、生成ログ、ビルド成果物を Wiki に含めない。
- 更新は Codex の OpenWiki 連携から行う。OpenWiki 用の GitHub Actions workflow は不要であり、無効化した雛形もリポジトリに残さない。生成ツールが `.github/workflows/openwiki-update.yml` や定期更新を前提とする案内を再作成した場合は、生成完了後に取り除く。

## モジュール説明ページの生成要件

- モジュールの説明は、単なる機能概要や変更箇所の案内で終わらせず、コードを開く前に主要な構成要素の役割と相互関係を理解できるものにする。以下の観点を、対象 module の規模と責務に応じて整理する。
- 調査では代表的な入口ファイルだけでなく、対象 module の production source 全体と、主要な呼び出し元・実装先・テストを確認する。ディレクトリ構造や既存の説明から構成要素を推測せず、実在する宣言と利用関係を根拠にする。
- 冒頭で module の目的、Domain / Data / UI 等の位置づけ、所有する概念・状態、公開する capability、依存先と利用者を説明する。Gradle module と Domain Context を安易に同一視しない。
- 「主要な構成要素」では class、interface、object、data class、sealed 型、enum、typealias、トップレベル関数・拡張関数を調べ、モデル、公開契約、UseCase、Domain Service、Repository 実装、adapter、UI、補助処理など役割ごとに整理する。公開 API を構成する型・関数は原則として網羅し、処理の理解に重要な内部実装も含め、名前・種類・責務・所属する主要メソッド・関連する構成要素・ソースリンクを表や小見出しで示す。小さな型や関数は役割が伝わる単位にまとめてよい。
- 「主要な API とメソッド」では公開メソッド・関数と、振る舞いを理解するうえで重要な内部メソッドを扱う。何を入力し、何を返し、どの状態や外部境界に作用するか、失敗時にどうなるかを必要な範囲で説明する。全メソッドのシグネチャや private helper を機械的に列挙する必要はない。
- 「構成要素間の関係」では interface と実装 class、利用者と依存先、生成・注入箇所、モデルの受け渡し、状態の所有者を明示する。別 module に実装がある契約は、確認できる具体実装と composition の接続先まで示す。本文中に登場する構成要素は「主要な構成要素」に含めるか、初出で役割と所在を説明する。型名や略称だけを唐突に登場させない。
- 「代表的な処理フロー」では入口となる class / method から主要な呼び出し先、状態更新、戻り先、失敗経路までを、実在する識別子を使って順序立てて説明する。複数の構成要素が協調する場合は Mermaid 図を適宜用い、図だけに依存せず文章でも意味を説明する。
- 説明の基本順序は「モジュールの位置づけと責務 → 主要な構成要素 → 主要 API と関係 → 代表的な処理フロー → 状態・失敗・境界 → 実装とテストへのリンク」とする。単純な module では節を統合し、大きな module では責務別の小見出しを設ける。説明されない識別子の羅列や、リンク集だけで終わるページは避ける。
- 完了前に、モジュール内の公開契約・主要構成要素と本文を照合し、重要な役割・接続関係・メソッドの説明漏れがないか確認する。実装から確認できない関係は推測で補完せず、未確認と明記する。生成物は source / test への導線であり、自動生成された API リファレンスの全文複製にはしない。
