1. 何を正本として読むか

このリポジトリでは、ADR を全部読み直して現在の構造を毎回再構成する方式を採らない。ADR-0122 により、判断履歴と現在形の説明を分離している。変更時は、情報の種類ごとに正本を使い分ける。

現在の構造・ルール

docs/architecture/ が入口。現在有効な layer、module ownership、Context、persistence、test、platform、AI、Web の規則を現在形で読む。

なぜそうしたか

docs/adr/ が Decision Log。Context、Decision、Consequences、Supersedes / Amends / Refines を追う。

機械可読な構成

settings.gradle.kts、config/architecture/*、Gradle verification が module や table ownership 等の構成値の正本。

現在の事実

実装と CI が最終的な実行状態。ただし Accepted ADR と矛盾する実装は「暗黙の設計変更」ではなく architecture drift として扱う。

この HTML は理解のための統合教材であり、新しい source of truth ではない。値が食い違う場合は、機械可読な構成・current architecture docs・Accepted ADR の関係を確認する。変更で設計判断そのものが変わるなら、この HTML だけを書き換えて済ませず ADR と current docs を更新する。

推奨する読み方

  1. このページで全体像と境界を理解する。
  2. 変更対象に対応する current document を読む。
  3. 判断理由が必要なら、その document の Sources から ADR へ遡る。
  4. module / table / framework-provider 等の構成値は machine-readable manifest と実装で確認する。
  5. 変更後は architecture verification と、その変更の owner が持つ最小の意味ある test を実行する。

根拠: ADR-0122 / architecture README / ADR-0162

2. 全体構造: 「feature が意味を所有し、app が接続する」

最も重要な見方は、画面やファイルではなく ownership から出発することにある。feature はアプリ固有の意味・状態・操作を所有し、core は横断的な技術 capability を提供し、app は Android application entry point と composition root としてそれらを接続する。

「複数 feature を使うから app に置く」は誤り。複数 source feature の状態を一つの triage surface にする Integrated の presentation policy は :feature:integrated:ui が所有する。app は source ViewModel の wiring、app-shell navigation、外部 Intent 等だけを接続する。

この設計で守りたい不変条件

  • feature 固有の変更理由が :app へ流出しない。
  • Domain が Android / SQLite / HTTP / concrete Data implementation を知らない。
  • 同じ物理 DB を共有していても、別 Context の table を直接読み書きしない。
  • application-scope runtime を Route / Worker ごとに再構築しない。
  • provider や external protocol の詳細を feature policy と混ぜない。
  • 機械判定できる境界違反は CI で落とし、意味判断が必要な ownership / privacy はレビューで補う。

UseCase を作る条件

「Layer を揃えるため」だけに転送用 UseCase を増やさない。次のように意味のある orchestration がある場合に使う。

  • 複数 Repository / capability の呼び出し順序が意味を持つ。
  • retry、partial success、集計、並列処理などの application rule がある。
  • 複数画面・entry point から同じ業務操作を再利用する。
  • Context 間 command の owner が操作全体の failure semantics を持つ。

interface / capability の粒度

consumer が Repository の一部しか必要としないなら、巨大な Repository をそのまま渡すより Reader / Writer / Query / Adder 等の目的を持つ narrow contract を優先する。Library の WebLibraryAdder はその例で、Bookmark は削除・再取得まで可能な WebLibraryMutator 全体へ依存しない。

根拠: principles.md / ADR-0001 / ADR-0125 / ADR-0186

4. Gradle module map: 物理 boundary と Domain boundary を混同しない

module 一覧の正本は settings.gradle.kts。feature module は ownership / build boundary であり、Bounded Context や Aggregate と 1 対 1 ではない。たとえば :feature:article は実装名として残るが、Domain 上は RSS Article より広い Content / ContentItem に近い。

Core modules

:core:background

background execution の共有技術 policy。Local AI と Cloud AI の pause control を分ける。

:core:database

connection、transaction、schema contribution / migration mechanism。feature schema の意味は所有しない。

:core:network

process-wide HTTP transport。application graph から feature / Worker へ共有。

:core:web-collector

内部 Web 取得の共有技術 capability。feature 固有 scraping semantics は持たない。

:core:ai-inference

provider-neutral な単発 text inference contract、model capability / progress。

:core:ai-cloud-openai

ChatGPT OAuth、Codex model catalog、Responses transport、OpenAI protocol、failure normalization。

:core:ai-runtime

Gemma / LiteRT-LM、tokenizer、Engine lifetime、benchmark、local vision/conversation 等。

:core:designsystem

共有 UI primitive / design system。

5. Domain Context map: 誰が意味と durable state を所有するか

Gradle feature は物理 ownership、Bounded Context は言語・model の境界、Aggregate は transaction と invariant の境界。この3つを混同すると「同じ module にあるから同じ Aggregate」「同じ DB にあるから自由に JOIN/write」という誤りが起きる。

RSS --------\
Reddit ------> Content (current :feature:article) ---> Curation / Summary / Knowledge
YouTube -----/           |                            (ContentItemId で参照)
                         |
                         +---- source metadata / reading state

Library: catalog / sources / SMB / Web metadata / organization
Health: Health Connect read model + Workout export capability
Workout: app-local workout state source of truth
Calendar: Android Calendar + Task + Workout の read-only date projection
Other: Asset / Task / Mail / Chat / Game
Supporting: AI Task Queue / Backup / Settings
Presentation composition: Integrated UI / Widget / Web delivery

Content

主要実装 :feature:article。content identity、URL/title/source metadata、published/fetched、reading state、classification override を所有。Bookmark 保存状態は持たない。

Curation

主要実装 :feature:bookmark。Bookmark、Tag、Folder、Read Later を所有。Bookmark→Web Library 移動 use case の操作 owner。

RSS / Reddit / YouTube

上流 Source Context。subscription、fetch/sync、authentication、source-specific semantics を所有。Content 書き込みは owner gateway を使う。

Summary

generated summary と task lifecycle / priority / provider routing の Summary-side rule を所有。Content/Curation table を直接参照しない。

Knowledge

Knowledge page、source relation、generated/edited state、background build lifecycle を所有。provider 選択も Knowledge の設定。

Library

Google Play Books / Kindle / Audible / SMB / Web を source とする catalog、整理 metadata、Web extractor、SMB normalization / cover workflow を所有。

Health

Health Connect は外部 source。read-only overview と、完了済み Workout の一方向 export capability。Health data を app durable table の共同 owner にしない。

Workout

アプリ内記録が source of truth。Health Connect への export 失敗や権限未付与でも local record は維持。

Calendar

独自 durable event table を持たない read-only projection。Android Calendar Provider、TaskReader、WorkoutReader を共通 CalendarEvent に投影。

Integrated

Domain data owner ではなく cross-feature presentation owner。複数 source の state/action を一画面へ投影・dispatch する意味を所有。

Context owner を決める問い

  • その状態を削除・復元・バックアップするとき、意味を説明できるのは誰か。
  • その操作の成功・失敗順序を誰が決めるべきか。
  • 別 source が増えても残る言葉は何か。
  • transactional invariant はどこまでを一単位として守る必要があるか。
  • 単に UI が同じ画面にあるだけで owner を統合していないか。

根拠: context-map.md / ADR-0106 / ADR-0123 / ADR-0186

7. Composition root と runtime lifetime

AppContainer は application-scope composition facade。HTTP client、database、AI runtime、feature repositories / schedulers など長寿命 object graph を一度だけ構築し、責務別の App*RuntimeDependencies へ分割している。

現行実装から読める runtime graph

YomitoriApplication / MainActivity
        |
        v
AppContainer
  ├─ HttpClient.create("Mosaic/${BuildConfig.VERSION_NAME} ...")
  ├─ YomitoriDatabase
  ├─ AppAiCoreRuntimeDependencies
  ├─ AppFeatureRuntimeDependencies          (container internal construction group)
  ├─ AppContentRuntimeDependencies
  ├─ AppSupportingRuntimeDependencies
  ├─ AppKnowledgeRuntimeDependencies
  └─ AppCrossFeatureRuntimeDependencies
        |
        +--> narrow factory / repository / scheduler / capability
                |
                +--> feature Route / WorkerFactory / platform adapter

runtime group 型は construction detail であり、Route / Screen / Worker へ「便利な bag」として渡さない。ADR-0162 では generic AppFeatureRuntimeDependencies を Route / Worker が直接取得しない guardrail を明示している。caller ごとに必要な narrow capability に投影する。

Route ownership

  • feature 内で ViewModel/Screen 接続まで完結できる root Route は :feature:<name>:ui が所有。
  • AppRouteDependencies は既存 caller contract の薄い facade。
  • content-facing construction は AppContentRouteDependencies、supporting/device-facing construction は AppSupportingRouteDependencies に分割。
  • app shell の AppSection / MainTab / AppViewModel は app UI ownership。
  • inactive tab の feature ViewModel を global host が eager activation しない。

MainActivity に残してよいもの

Android lifecycle、external Intent、OS permission、app-level navigation、crash diagnostics など platform entry-point 責務。

残してはいけないもの: feature ViewModel ownership、concrete feature.*.data.* import、feature business rule。

「DI framework がない」ことの意味

明示的 constructor / factory wiring を使い、service locator を導入しない。Android が直接生成する Activity / Service / AppWidgetProvider 等で constructor injection ができない場合だけ、監査済み narrow Provider boundary を利用できる。WorkManager Worker はこの例外に含めない。

根拠: module-map.md / principles.md / ADR-0144 / ADR-0162

8. Persistence: 物理 DB は一つ、ownership は一つではない

durable user data は原則単一 SQLite database を共有するが、同じ file / transaction / foreign key に存在することは共同 ownership を意味しない。DB compatibility baseline は現在 v27。fresh install は各 feature の schema definition が正本で、v27 到達以前の historical migration は current runtime から削除済み。

Schema contribution model

:core:database
  connection / transaction / DatabaseSchemaContribution / migration runner
        ^
        |
:feature:<owner>:data
  feature table/index schema + migration meaning + explicit initializer
        ^
        |
:app
  contributions を集約し single DB version / order を composition
  • feature-specific table/index schema と migration は owner data module。
  • Worker / Service は独自 schema composition を持たない。
  • Repository の snapshot() 等の read side effect を schema initialization contract にしない。
  • 同一 table の CREATE 定義を Repository と schema contribution に複製しない。
  • 新 durable table は config/architecture/table-ownership.tsv に必ず登録。
  • 現在 foreign-table-access-allowlist.tsv に runtime exception entry はない。

Backup / cache

  • backup は current application schema と同じ DB version の snapshot を復元対象とし、異なる schema version は restore 前に拒否。
  • SMB cover image は再生成可能 cache で、DB snapshot 本体へ画像を含めない。
  • restore 後の Library cache invalidation は Backup が Library-owned LibraryBackupRestoreInitializer を呼ぶ。Backup が Library table を直接 write しない。
  • credential は backup 対象外。restore 直後に SMB work を勝手に再開せず、credential 再設定後に owner 経路で再 queue。

Schema change をするときの必須判断

  1. Domain / Context owner は誰か。
  2. owner data module の schema と explicit initializer を同じ定義にする。
  3. DB version bump が必要か、additive idempotent refinement で足りるか。
  4. current v27→next の migration / restore baseline をどこまで維持するか。
  5. foreign access を新設していないか。
  6. manifest / architecture verification / integration test を更新したか。

根拠: persistence.md / table-ownership.tsv / ADR-0047 / ADR-0098 / ADR-0138

9. Background execution / WorkManager: Worker は feature の entry point、global lookup の場所ではない

feature 固有 Worker、WorkerFactory、scheduler/controller、queue-state interpretation は owning feature の data/runtime 側へ置く。app は feature factory を application-scope graph へ接続する。

WorkManager
   |
   v
App DelegatingWorkerFactory
   |
   v
Feature-owned WorkerFactory
   |  constructor injection
   v
Feature Worker
   |
   v
UseCase / Repository / scheduler from AppContainer graph

守ること

  • Worker 内で database / Repository graph を並行構築しない。
  • Application as? XxxProvider で service locator 的に dependency を取得しない。
  • feature WorkerFactory は concrete implementation を作らず、app が既存 graph と接続する。
  • enqueue 済み work の Worker FQCN は framework identity。DI 方式だけ変えるとき不用意に class identity を変えない。
  • 旧 app package FQCN 用の compatibility Worker shim は current baseline では維持しない。必要になったら期間と終了条件を ADR に記録。

Local AI background と Cloud AI background

Local と Cloud は pause control と constraint が別。Local は charging resume semantics を持てるが、Cloud pause に同じ意味を持たせない。Summary / Knowledge の provider 選択が変わる場合は、queue 表示だけでなく gate、network constraint、実 inference 先まで同じ snapshot / setting と整合させる。

根拠: principles.md / testing.md / ADR-0146 / ADR-0172

10. AI runtime: provider protocol と feature policy を分離する

責務分割

:core:ai-inferenceprovider-neutral single-shot text inference contract / model capability / progressSummary prompt、Knowledge build policy
:core:ai-runtimeLocal model runtime、Gemma/LiteRT-LM、Engine lifetime、tokenizer 等feature-specific routing/prompt
:core:ai-cloud-openaiChatGPT OAuth、Codex catalog、Responses protocol、OpenAI transport、raw failure normalizationSummary/Knowledge task semantics

ChatGPT failure boundary

provider の raw response/error を feature へそのまま渡さない。ChatGptInferenceClient が transport/OAuth/HTTP failure を次の安定 taxonomy に正規化する: transient、rate limited、authentication、request rejected、not connected、requested Web target not opened、unknown。

typed failure に残すのは kind、retryable、必要時の HTTP status 程度。provider response body、prompt、token、account id、対象 URL の raw detail を feature error へ保持しない。WorkManager retry / durable task state / user message は owning feature が意味づける。

Application-scope lifetime

Local model manager、ChatGPT client、inference adapter、feature repository は AppContainer 配下で一度構築し再利用。runtime group 自体を consumer へ配らず、inference capability / factory / scheduler 等に狭めて渡す。

High-memory local vision の process boundary

SMB 書誌正規化の GPU vision inference は main process と分離した private bound Service へ隔離する。main process は durable queue、foreground execution、DB transaction、priority を保持し、vision process へ大きな image bytes を Binder で送らず app-private cache path と小さい metadata/prompt を渡す。Service 側でも canonical path / size を再検証する。

  • vision Engine は専用 process 内で限定的に再利用。
  • batch 終了時は Service / process を終了し native memory を OS へ返す境界にする。
  • secondary process の Application から main-process 専用 observer / diagnostics / scheduling を起動しない。
  • 診断へ raw user content、画像 payload、表紙 path、prompt、AI output を保存しない。
AI の変更では「model を変える」だけを見ない。provider contract、routing owner、queue snapshot、background constraint、application-scope lifetime、memory/process boundary、failure sanitization のどこが変わるかを先に分類する。

根拠: ai-runtime.md / ADR-0165 / ADR-0172 / ADR-0185

11. Web content: ユーザー閲覧と内部取得は別 capability

用途選択Owner / 理由
RSS / Bookmark Article をユーザーが閲覧Custom Tabs:app launcher。既定ブラウザを尊重、HTTP/HTTPS のみ。
Web 由来 Library item をユーザーが閲覧Custom Tabs同上。source-specific app link は各 source routing を維持。
Library static metadataHTTP(S) OGP/HTMLLibrary data。まず軽い static path。
Library rendered metadata / custom extractor短命 WebViewLibrary-owned workflow。専用 profile、timeout/watchdog。
RSS synthetic feed scrapinguser-defined rule + WebView acquisitionRSS-owned semantics / durable rule。
X viewer 等 app-controlled renderingfeature-owned WebViewfeature 固有 workflow / CSS / renderer recovery。

RSS acquisition の現在の2経路

  1. URL に一致する user-defined Web scraping rule。
  2. 通常の RSS / Atom discovery / fetch。

組み込み site-specific synthetic feed client は ADR-0184 で廃止済み。custom rule がなければ旧 MangaOne / Yanmaga 等の site-specific path へ fallback しない。host 名を根拠に暗黙の COMIC 分類もしない。

Library Web metadata

  • 通常は static HTTP(S) OGP/HTML を優先。
  • metadata 不足時は短命 WebView。
  • matching WebLibraryMetadataExtractor がある場合は user-defined Promise function を専用 WebView profile 内で実行し site-specific override として使う。
  • extractor があるときは static metadata が揃っていても rule を実行する。
  • native JavaScript bridge を公開しない。
  • multiple refresh は WebView を同時大量起動せず直列化。

Renderer lifecycle

  • onRenderProcessGone 後の WebView instance を再利用しない。
  • system low-memory kill と renderer crash を区別する。
  • headless adapter は renderer loss / timeout を現在取得単位の retryable/failure として返す。
  • foreground Activity が必要な rendered client は Activity 復帰まで待つ。
  • JavaScript polling だけに停止責務を依存せず native timeout/watchdog を持つ。

ユーザー定義 rule は user data

実 URL pattern、DOM selector、JavaScript function code は repository source、ADR、fixture へコピーしない。RSS rule と Library extractor は実行パターンが似ていても、共有 table/repository に統合しない。feed semantics と bibliographic metadata semantics は別 owner。

根拠: web-content.md / ADR-0163 / ADR-0173 / ADR-0180 / ADR-0182 / ADR-0184

Android 17 / API 37 は現行の実行環境としてサポート対象だが、targetSdk 37 はまだ採用していない。理由は SMB と LAN Web Server が local network を使い、Android 17 target では ACCESS_LOCAL_NETWORK runtime permission UX が必要になるため。target 37 は permission UX、拒否時の説明、SMB discovery/connection、cover prefetch、LAN Web Server integration、target-specific behavior を同じ migration で検証する設計変更として扱う。

minSdk 34 が意味すること

  • API 33 以下だけを支える fallback / SDK_INT branch を新設しない。
  • API 35/36/37、extension capability など supported range 内で実差がある guard は維持可能。
  • Health Connect は単純 API level ではなく feature status / provider capability で availability を見る。
  • 全 Android application/library module の minSdk >= 34 を architecture verification で固定。

App-wide authentication boundary

  • app lock は既定無効、Settings から明示有効化。
  • 有効化時は BIOMETRIC_STRONG 登録を確認。
  • 通常解除は BIOMETRIC_STRONG | DEVICE_CREDENTIAL で recovery path を残す。
  • 設定 UI は Settings、authentication lifecycle / app-shell gate は app owner。
  • ロック中は feature content / startup crash diagnostics を描画せず、share/widget Intent も認証成功後まで遅延。
  • Custom Tabs 起動直後の一時的 onStop は one-shot marker で再ロックを抑制し、通常 background と区別。
  • ロック有効時の非表示では FLAG_SECURE により recent-app preview へ内容を残さない。
  • 永続化するのは enabled flag のみ。認証済み状態や biometric data は保存しない。

LAN Web Server

:feature:web:data が concrete mutable server state を所有し、責務を分割する。

  • LanWebServer: socket / HTTP parse / LAN validation / token-cookie auth / route dispatch / security headers。
  • LanWebReadModel: owner Repository contract から read-only model を構築。
  • LanWebRenderer: typed model から escaping 付き HTML rendering。

bootstrap token は service lifetime の一度きり URL query、成功時に session cookie へ移行。server stop で token を失効。HTTP 自体は暗号化されないため trusted LAN 前提。

Process / crash diagnostics

  • main process と app-owned secondary process を区別し、WebView sandbox renderer の low-memory exit を app process failure として誤分類しない。
  • Android 17 memory limits は targetSdk と無関係に runtime constraint として扱う。
  • API 37 runtime では ProfilingManager anomaly trigger を guard 下で利用できるが、artifact は app-private storage。
  • shareable report は URL、email、credential-like value、Bearer token、private path を sanitize。
  • profile/heap artifact 本体は public repository へ入れない。

13. Public repository / Security boundary

15. 責任を持って変更するための実践手順

新機能でも bug fix でも、最初にファイルを選ばない。変更理由を ownership と contract に分解してから実装場所を決める。

ユーザーに見える変更を一文で定義する

「どの状態が、どの操作で、どう変わるか」。UI 文言や class 名ではなく product/domain の言葉で書く。

Domain / Context owner を決める

Content、Curation、RSS、Library、Summary、Knowledge、Health、Workout 等のどこが意味・failure semantics・durable state を所有するか。

Layer を分解する

presentation、pure rule/use case、contract、data adapter、Android/platform の各変更点を分ける。単なる転送 UseCase は作らない。

Cross-context interaction を分類する

command / read / projection のどれか。owner の narrow capability で済むか。foreign table を触る設計になっていないか。

Lifetime を決める

screen scope、feature/root ViewModel、application scope、Worker lifetime、separate process のどれか。long-lived resource を重複生成しない。

Persistence impact を確認する

新 durable table/column、migration、backup restore、cache invalidation、table ownership manifest、v27 baseline からの互換性。

Platform / Web / AI の特殊 boundary を確認する

WorkManager DI、Custom Tabs vs WebView、renderer loss、provider-neutral AI contract、local/cloud routing、memory/process isolation、permissions。

テストを「変更した契約」に割り当てる

Domain unit、UseCase unit、Repository integration、Projection integration、architecture fixture、Android framework-aware test のどれが必要か。

Public repository review を独立して行う

secret scan だけでなく、実ユーザーデータ・private URL・diagnostic artifact・backup 等を意味的に確認する。

Architecture documentation / ADR を判定する

既存決定の範囲内の実装なら docs の整合のみ。新しい設計選択・既存 decision の変更なら ADR を追加/改訂し、current docs と executable guardrail も同期。

CI と差分を最終レビューする

想定外 module/Context へ差分が広がっていないか、test が owner にあるか、compatibility code を不用意に増やしていないかを確認。

設計変更かどうかの目安

ADR が通常必要

dependency direction、Context ownership、persistence owner、runtime lifetime/process、provider routing semantics、platform baseline、security model、compatibility baseline の変更。

ADR が通常不要

既存 decision に沿った UI 改善、局所 bug fix、同じ contract 内の adapter修正、documentation-only 教材追加。ただし current docs の事実が変わるなら更新する。

17. 実践問題: 変更をどこへ置くか

答えを見る前に、owner → layer → contract → persistence/runtime → test の順で考える。

問題1: RSS 記事から「ブックマーク保存」を追加したい。RSS data から bookmarks table に INSERT してよいか。

不可。Curation/Bookmark owner の command/capability を使う。RSS は source semantics を所有するが Bookmark persistence owner ではない。UI action が RSS 画面にあっても、mutation は Bookmark owner へ委譲する。cross-context contract と use-case semantics を unit test、必要な wiring を architecture rule で確認する。

問題2: Bookmark を Web Library へ移動する。両 feature を知る transfer service を app に置くべきか。

現行 decision では不要。Bookmark-owned MoveBookmarkToLibraryUseCase が Library の narrow WebLibraryAdder を使い、Library 追加成功後だけ Bookmark を解除する。Library→Bookmark は提供しない。ADR-0186 の一方向 ownership が正本。

問題3: Library の新しい durable metadata column を追加する。

:feature:library:data が schema owner。fresh schema と explicit initializer の同一定義、必要なら v27 以降 migration、backup compatibility、table ownership manifest（新 table の場合）、integration test を確認する。Backup や app が Library table を直接操作してはいけない。

問題4: Article の外部 HTTP URL を app 内で見たいので WebView Screen を作る。

通常のユーザー閲覧なら現行 decision は Custom Tabs。app の launcher が HTTP/HTTPS を開き、feature は CustomTabsIntent を直接所有しない。WebView は scraping / metadata extraction / X viewer 等、app-controlled workflow が必要な場合に限定。

問題5: Summary の ChatGPT 失敗時に OpenAI response body を snackbar へ表示する。

不可。raw provider failure は :core:ai-cloud-openai で stable taxonomy に正規化し、feature は typed failure を Summary-specific state/message へ写像する。response body、prompt、token、account id、対象 URL 等を保持しない。

問題6: 新しい Worker が Repository を必要とするので Application を cast して取得する。

不可。WorkManager Worker は framework-provider lookup の例外ではない。owning feature data module の WorkerFactory が constructor injection し、app DelegatingWorkerFactory が AppContainer の application-scope graph と接続する。

問題7: RSS/Reddit/YouTube/Mail の共通一覧に新 action を追加する。

Integrated presentation semantics なら :feature:integrated:ui が owner。projection/dispatch/item action をそこで変更する。app に置くのは app-shell navigation、external Intent、dependency wiring 等の application-only callback。pure projection semantics は JVM unit test で固定。

問題8: API 37 の機能を使うため targetSdk 37 へ上げる。

単純 version bump ではない。SMB/LAN Web Server の ACCESS_LOCAL_NETWORK runtime permission UX、拒否時の表示、integration/実端末確認、target-specific behavior、大画面制約を同じ platform migration として設計・ADR/current docs/verification を更新する。

問題9: Calendar 画面を高速化するため Task table を直接 JOIN する。

Calendar は Task owner ではなく read-only projection。まず TaskReader 等 owner read API を利用する。合成が計測上問題で、named Projection が必要なら purpose/read-only/referenced tables を明示し integration test と設計根拠を持たせる。

問題10: 実端末で失敗した Web extractor の JS をそのまま regression fixture に保存する。

原則不可。ユーザー設定の URL pattern/selector/function code は user data。失敗の構造を再現する synthetic HTML / JS / URL を作る。public repository verifier に加え意味的 privacy review を行う。

20. 変更前・PR前・merge前の責任ある変更チェックリスト

設計

  • □ 変更理由を product/domain の言葉で説明できる。
  • □ Domain/Context owner を特定した。
  • □ feature module と Bounded Context/Aggregate を機械的に同一視していない。
  • □ UI / Domain / Data / Core / App の責務が混ざっていない。
  • □ cross-context operation は owner の purpose-specific contract を通る。
  • □ app に feature semantics を置いていない。
  • □ generic runtime bag / service locator を新設していない。

Persistence / runtime

  • □ durable data の owner と schema contribution が一致する。
  • □ foreign table write をしていない。
  • □ read-only Projection を使うなら目的・測定根拠・参照 table・integration test がある。
  • □ current v27 compatibility / backup baseline への影響を確認した。
  • □ long-lived runtime を Route/Worker ごとに重複構築していない。
  • □ Worker dependency は WorkerFactory constructor injection。
  • □ high-memory resource の lifetime/process boundary を明示した。

Platform / Web / AI

  • □ minSdk 34 未満専用 fallback を増やしていない。
  • □ targetSdk/API behavior change は permission/UX/integration まで確認した。
  • □ user-visible external HTTP/HTTPS は原則 Custom Tabs。
  • □ WebView は renderer loss / timeout / foreground lifecycle を扱う。
  • □ provider protocol と feature policy を分離している。
  • □ raw provider error / user content を diagnostics に残していない。

Test / documentation

  • □ 変更した契約の owner に最小で意味のある test がある。
  • □ architecture rule を変えたなら fixture/verification も変えた。
  • □ module map / table manifest / framework-provider manifest を必要に応じ同期した。
  • □ design decision が変わるなら ADR を追加/改訂した。
  • □ current architecture docs の現在形を同期した。
  • □ historical ADR の Supersedes/Amends/Refines を確認した。

Public repository

  • □ credential/token/keystore/OAuth secret を含まない。
  • □ 実ユーザー URL/email/book/health/private identifiers を fixture/docs に固定していない。
  • □ backup/database/profile/heap artifact を含まない。
  • □ user-defined scraping/extractor rule を source に転記していない。
  • □ automated public-repository verifier と独立した意味的 review の両方を行った。
このチェックを通せる状態なら、「どこを変えれば動くか」だけでなく「なぜそこが owner で、どの boundary を壊さず、どの test で責任を持つか」を説明できる。それがこのプロジェクトで変更を担当するための最低限の理解水準である。
