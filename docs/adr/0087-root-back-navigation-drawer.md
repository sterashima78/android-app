# ADR-0087: ルート Back をドロワー表示とアプリ終了の二段階操作にする

- Status: Accepted
- Date: 2026-08-17
- Amends: ADR-0012

## Context

アプリの各トップレベル画面は単一の `MainActivity` と `YomitoriApp` の下で切り替えている。現在、画面上でシステム Back を実行すると、アプリ共通の戻る処理がないため Activity の終了へ進み、現在のセクションから別のセクションへ移動したい場合でもアプリが閉じてしまう。

ADR-0012 では、一覧項目や WebView の横スワイプと競合しないよう、閉じているドロワーを横スワイプで開かず、ハンバーガーメニューから明示的に開く方針を採用した。同 ADR はシステム Back をドロワーを閉じる経路として扱っていたが、トップレベル画面からの Back を安全なナビゲーション導線として利用する今回の要件とは一致しない。

## Decision

アプリ共通の Back 操作は `YomitoriApp` のルート UI が管理し、次の二段階動作とする。

1. ドロワーが閉じている状態で Back を実行した場合、その Back を消費して `DrawerState.open()` を呼び、ドロワーを表示する。
2. ドロワーが開いている状態で Back を実行した場合、ドロワーを閉じずに Activity を終了する。

Activity の終了処理自体は UI が `Activity` を直接参照せず、`MainActivity` から `onExitApp` コールバックとして渡す。これにより、ルート UI は「終了を要求する」という UI 上の判断だけを持ち、Android Activity のライフサイクル操作は Activity 側に残す。

ドロワーが閉じている間の `gesturesEnabled = false` は ADR-0012 の方針を維持する。したがって、画面左端からの横スワイプではドロワーを開かない。ハンバーガーメニューも従来どおりドロワーを開く経路として維持する。

ドロワーが開いている間の scrim タップ、閉じる方向のドラッグ、項目選択による閉じ方も維持する。ただし、システム Back だけはドロワーを閉じる操作ではなく、アプリ終了操作として扱う。

ダイアログ、ボトムシート、または各機能が将来独自の Back 処理を持つ場合は、それらのより内側の Back 処理を優先する。ルートの二段階動作は、より具体的な UI が Back を消費しない場合に適用する。

## Consequences

### Positive

- トップレベル画面で誤って Back を実行しても、直ちにアプリが終了せず、まずアプリ内ナビゲーションへ戻れる
- すべてのセクションで同じ Back 操作になり、feature ごとに例外処理を持たなくてよい
- 横スワイプとドロワーの競合を避ける ADR-0012 の目的を維持できる
- ドロワー表示後にもう一度 Back を実行すれば、明示的にアプリを終了できる

### Negative

- Android の一般的な「開いているドロワーで Back を押すとドロワーを閉じる」挙動とは異なる
- Back でアプリを終了するには、通常状態からは二回の操作が必要になる
- ルートより内側に Back 処理を追加する UI は、ルート操作との優先順位を意識する必要がある

## Relationship to existing ADRs

- ADR-0012 を一部変更する。閉じたドロワーを横スワイプで開かない判断は維持する一方、「ドロワーを開く経路をハンバーガーメニューに限定する」と「開いたドロワーをシステム Back で閉じる」という判断は本 ADR で置き換える。
- ADR-0001 の UI 層の責務に従い、アプリ共通の navigation interaction はルート UI で扱う。
- ADR-0003 / ADR-0004 の feature 分離を維持し、各 feature にアプリ終了やドロワー制御の責務を持ち込まない。
