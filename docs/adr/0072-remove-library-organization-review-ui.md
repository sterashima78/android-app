# ADR-0072: 蔵書AI整理の仕分け待ちUIを廃止し既存未確定候補を破棄する

- Status: Accepted
- Date: 2026-08-16

## Context

ADR-0066 では一括蔵書AI整理の結果を `PENDING_REVIEW` / `DEFERRED` として保持し、専用の候補レビューUIで採用・編集・保留・却下する方式を採用した。

その後 ADR-0111 で、一括バックグラウンド整理は構造化出力を検証したうえで承認待ちなしに自動反映する方針へ変更した。通常経路では候補レビューを行わないため、旧レビューUIと既存の未確定候補は現在の操作モデルと一致しない。

## Decision

### 1. 一括整理の候補レビューUIを削除する

`LibraryOrganizationDialog` から「候補を仕分け」導線と、候補一覧・候補編集・採用・保留・却下の専用UIを削除する。

一括整理画面では次だけを扱う。

- 未整理蔵書のバックグラウンド整理開始
- 実行状況の確認
- 一時停止・再開
- 完了後の未整理蔵書の再解析

単冊の通常編集と「AIで整理候補を作る」操作は維持する。これは一括整理の仕分け待ちUIとは別の、ユーザーが明示的に開始する編集支援である。

### 2. 既存の未確定候補はDB v18移行時に破棄する

DB version を17から18へ上げ、`library_organization_batch_items` の次の状態を削除する。

- `PENDING_REVIEW`
- `DEFERRED`

これらの候補に含まれるタグ・コレクション・reasonは引き継がず、一律に破棄する。すでに `APPLIED` となった整理結果、`FAILED` / `SKIPPED`、実行待ちの `QUEUED` / `PROCESSING` は削除しない。

未確定候補の削除後、`RUNNING` / `PAUSED` のバッチに `QUEUED` / `PROCESSING` が残っていなければ、そのバッチを `COMPLETED` にする。これにより旧レビュー待ちだけを理由にバッチが永久に停止しないようにする。

### 3. 失敗した自動整理は共通AIタスクキューから再試行できる

`FAILED` / `SKIPPED` を確認・再試行するために旧候補レビューUIを残さない。ADR-0070 の共通AIタスクキューにある1冊単位の再試行を利用できる。

一括整理画面には失敗・スキップ件数だけを表示する。ユーザーが「未整理を再解析」を選んだ場合は、前回バッチの `FAILED` / `SKIPPED` を `REJECTED` として終了させ、現在も未整理の本を新しいバッチへ再投入する。これにより、旧レビューUIで「却下して完了」する操作を要求せずに一括再実行できる。

同様に、DB移行後や異常終了によって `PENDING_REVIEW` / `DEFERRED` が残っている場合も、新しいバッチ開始前に `REJECTED` として終了させる。`QUEUED` / `PROCESSING` が実際に残っている実行中バッチだけは新規バッチ開始を許可しない。

### 4. 候補状態の永続モデルは直ちには削除しない

`PENDING_REVIEW` / `DEFERRED` enumや候補操作APIは、自動反映処理の短い中間状態、既存DBとの互換性、段階的なコード整理のためこの変更では物理削除しない。ただし通常UIからは到達不能とし、新しいユーザー操作フローとして利用しない。

将来、ADR-0111 の自動反映経路を完全に単一transactionへ統合した時点で、不要な候補状態と操作APIの削除を別途検討する。

## Supersedes

- ADR-0066 section 3 の候補をユーザーが仕分けるUIを廃止する。
- ADR-0111 section 2 の「異常時に既存UIから未確定候補を確認・処理できる」という判断を廃止する。既存の未確定候補は移行時に破棄し、失敗は共通AIタスクキューまたは新しい一括再解析から扱う。

ADR-0111 の一括自動反映、JSON検証、シリーズ分類再利用は維持する。

## Consequences

### Positive

- 大量の自動整理結果を承認する旧操作モデルがUIから消える。
- アップデート前に残っていた仕分け待ち候補で新しいバッチが止まらない。
- 一括整理画面の責務が開始・停止・進捗確認に限定される。
- 失敗は共通AIタスクキューから個別再試行するか、未整理本としてまとめて再解析できる。

### Negative

- 既存の `PENDING_REVIEW` / `DEFERRED` 候補は復元できない。
- 新しい一括再解析を開始すると、前回の `FAILED` / `SKIPPED` タスクは `REJECTED` となり、前回バッチとしての個別再試行対象ではなくなる。
- 候補状態enumと一部repository APIは当面残るため、内部モデルには旧フローの痕跡が残る。

## Public repository safety

DB migration、UI文言、テストには一般化した架空データだけを使用する。実在する蔵書名、ASIN、Personal Document ID、ユーザー固有タグ・コレクション、認証情報は追加しない。
