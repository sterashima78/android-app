# ADR-0111: 一括蔵書AI整理を自動反映し構造化出力とシリーズ文脈で分類品質を守る

- Status: Accepted
- Date: 2026-08-16

## Context

ADR-0108 と ADR-0066 では、AIが生成した蔵書整理候補をユーザーが確認してからタグ・コレクションへ反映する方針を採用した。これは少数件を対象にする場合は安全だが、一括整理では数十〜数百冊の候補を1冊ずつ承認する必要があり、実用上の負担が大きい。

また、現在のプロンプトはJSON出力を要求しているものの、パーサは `tags` や `collections` の型が不正な場合でも空配列として扱える余地があった。例えば配列ではなく、複数タグを1つの文字列へカギ括弧付きで連結した出力を、明確な生成失敗として検出できない。

さらに書誌データにはシリーズ名を含めているが、すでに整理済みの同一シリーズ書籍がどのタグ・コレクションを使っているかはAIへ明示していない。同じシリーズの本では分類を再利用できる可能性が高く、既存分類の表記揺れ抑止にも利用できる。

## Decision

### 1. 一括バックグラウンド整理は承認待ちせず自動反映する

`LibraryOrganizationBatchWorker` が1冊のAI整理候補を正常に生成した場合、その候補を永続化した直後に既存の `acceptCandidate` 経路でタグ・コレクションへ反映し、通常は `APPLIED` まで進める。

一括整理中にユーザーが同じ本を手動整理した場合は手動変更を優先し、AI候補で上書きしない。競合を検出したAI候補は `REJECTED` として完了扱いにし、承認待ちによって次のバッチを止めない。

AIは従来どおり読書状態を推測しない。自動反映時も `acceptCandidate` が現在の読書状態を保持する。

単冊の「AI候補を生成」操作はこの変更の対象外とし、従来どおりユーザーが候補を確認・編集して保存する。

### 2. 候補テーブルは監査・復旧状態として維持する

`library_organization_batch_items` は削除しない。正常経路では `PROCESSING -> PENDING_REVIEW -> APPLIED` を短時間で通過するが、生成結果、reason、失敗状態、再試行状態を保持するdurable task recordとして引き続き利用する。

WorkerのキャンセルやDBエラーが候補永続化と自動反映の間で発生した場合、`PENDING_REVIEW` が残ることを許容する。これは通常の承認フローではなく異常時の復旧状態として既存UIから確認・処理できる。

`FAILED` と `SKIPPED` の個別再試行、および共通AIタスクキューへの1冊単位投影はADR-0070のまま維持する。

### 3. AI出力は厳密なJSON Schema相当の検証を通す

蔵書整理の出力契約を次に固定する。

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["tags", "collections", "reason"],
  "properties": {
    "tags": {
      "type": "array",
      "maxItems": 5,
      "items": { "type": "string", "minLength": 1, "maxLength": 80 }
    },
    "collections": {
      "type": "array",
      "maxItems": 2,
      "items": { "type": "string", "minLength": 1, "maxLength": 80 }
    },
    "reason": { "type": "string", "maxLength": 240 }
  }
}
```

モデルにはMarkdownコードフェンスや説明文を付けず、JSONオブジェクトだけを返すよう要求する。実装では `kotlinx.serialization.json` でJSONとして厳密にparseし、ルート型、必須フィールド、追加フィールド、配列型、要素型、件数、文字数を検証する。

不正な出力を暗黙に切り詰めたり空配列へ変換したりしない。検証に失敗した場合は、検証エラーを短くモデルへ返して1回だけ再生成する。再生成後も不正ならその本のタスクを `FAILED` とし、既存の1冊単位再試行を利用する。

不正なモデル出力そのものは再生成プロンプトへ埋め込まず、検証エラーだけを渡す。これにより不要な入力増加と、モデル自身の壊れた書式を再模倣する可能性を避ける。

### 4. 同一シリーズの確定済み分類を専用文脈として渡す

対象本にシリーズ情報がある場合、蔵書snapshotから同一シリーズの別書籍を探し、そのうち確定済みのタグ・コレクションを `seriesContext` として通常のtaxonomyとは別にAIへ渡す。

シリーズ一致は次の順序で判定する。

- 両方に構造化series IDがある場合はID一致を使う
- どちらかにseries IDがない場合だけ正規化したシリーズ名へフォールバックする
- 両方に異なるseries IDがある場合は、表示名が同じでも同一シリーズとみなさない

AIには、書誌情報から明確に不適切と判断できる場合を除き、同一シリーズで既に使われている分類を優先再利用させる。

一括整理で先に自動反映されたシリーズ本は確定済み分類になるため、後続の同シリーズ本も同じ分類を参照できる。

### 5. 人による大量修正は別の編集ワークフローとして扱う

自動反映を採用する代わりに、AI整理結果を人が後から効率よく直す操作を別タスクとして実装する。Issue #123 で、直近のAI整理結果の絞り込み、複数選択、タグ・コレクションの一括追加／削除、シリーズ単位編集を検討する。

この編集UIはAI承認ゲートではなく、確定済みユーザー整理状態を直接編集する通常のLibrary機能として扱う。

### 6. 公開リポジトリへ実ユーザーデータを追加しない

JSON Schema、テスト、ADRには架空の値だけを使う。実在する蔵書名、ASIN、Personal Document ID、ユーザー固有タグ・コレクション、AI生成結果、認証情報をfixtureやログへ追加しない。

AI推論と再生成は引き続き端末内ローカルモデルだけで行い、書誌情報や分類を外部AIサービスへ送信しない。

## Supersedes

- ADR-0108 の「AI候補は自動適用しない」という判断のうち、一括バックグラウンド整理に関する部分を本ADRで置き換える。単冊候補の確認式UIは維持する。
- ADR-0066 section 3 の「通常の一括候補をユーザーが1冊ずつ仕分ける」ことを必須とする判断を廃止する。候補状態と既存UIは異常時復旧・履歴互換のため残す。
- ADR-0066 section 5 のtaxonomy再利用方針を拡張し、確定済み分類に加えて同一シリーズの分類を専用文脈として扱う。
- ADR-0070 の1冊単位タスク表示、durable task state、バックグラウンドAI直列化は維持する。

## Consequences

### Positive

- 大量の蔵書を整理する際に1冊ずつ承認する必要がなくなる。
- 配列ではないタグ表現や余計な説明文などを明確な不正出力として検出できる。
- 不正出力は1回自動修復を試みるため、軽微な生成揺れで即座に手作業へ戻りにくい。
- 同じシリーズでタグ・コレクションの一貫性が高まり、分類名の増殖を抑えやすい。
- 既存のdurable queue、再試行、読書状態保護を再利用できる。

### Negative

- AIの誤分類も自動反映されるため、後からまとめて修正するUIが重要になる。
- 正常経路でも候補永続化と自動反映は2段階なので、ごく短い中間状態が存在する。
- JSON出力が2回連続で不正な本はFAILEDとなり、個別再試行が必要になる。
- シリーズ最初の1冊に既存分類がない場合、その本自身にはシリーズ文脈を利用できない。

## Relationship to existing ADRs

- ADR-0030: 既存分類をAIへ提示して分類語の増殖を抑える原則を継承する。
- ADR-0056: JSON検証、再生成、シリーズ分類policyはLibrary featureに置き、`core:ai-runtime` は汎用推論に留める。
- ADR-0108: 蔵書整理モデルと単冊候補UIを維持し、一括自動適用だけを変更する。
- ADR-0066: durable batch/item table、WorkManager実行、失敗・再試行状態を維持する。
- ADR-0070: 共通AIタスクキューへの1冊単位投影と推論直列化を維持する。
