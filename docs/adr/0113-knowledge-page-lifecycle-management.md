# ADR-0113: LLM Wikiの記事削除・分割・統合をユーザー管理操作として扱う

- Status: Accepted
- Date: 2026-08-16

## Context

ADR-0109で、Knowledgeの自動生成記事とLLM Editorによるユーザー管理記事を導入した。一方、自動生成では不要な記事が作られる場合があり、記事が大きくなりすぎた場合の分割や、内容が重なる記事の統合も必要になる。

単純な削除では、自動生成記事が次回の自動Wiki再構築で同じトピックから復活する。また、分割・統合をLLMの再生成だけで実装すると、長文記事ほどコンテキスト上限の影響を受け、既存本文や引用を不必要に変化させる可能性がある。

## Decision

記事詳細に「削除」「分割」「統合」を追加する。これらはLLM Editorとは別の、ユーザーによる記事ライフサイクル管理操作とする。

### 削除

ユーザーが新規作成した記事や分割で作成した記事など、ユーザー操作で新しいIDを割り当てた記事は物理削除する。

自動トピック由来の決定論的IDを持つ記事は、LLM Editorで編集済みの場合も含め、物理削除ではなくeditor-managedの削除済みマーカーへ変換する。削除済みマーカーは通常の一覧・詳細取得から除外するが、自動Wiki再構築ではeditor-managed記事として認識されるため同じ自動トピックを再生成しない。

削除済みマーカーはユーザーの明示的な意思を表すため、既存のeditor-managed Knowledgeバックアップ対象に含める。これによりバックアップ復元後も不要記事が再生成されない。

### 分割

分割はLLM推論を使わず、MarkdownのH2 (`##`) 見出しを境界に行う。選択した見出しより前を元記事へ残し、見出し名を新しい記事タイトルとして、その見出し以降を新しい記事へ移す。

分割後の両記事はeditor-managedとする。元記事の出典を両方へ引き継ぐ。これにより、現在のモデルで全文編集できない長文記事でも分割でき、分割処理自体が本文の再生成を起こさない。

### 統合

統合先は現在開いている記事とし、ユーザーが別の記事を一つ選択する。統合先のタイトルを維持し、統合元の記事をH2節として末尾へ追加する。本文はLLMで再生成しない。

両記事の出典はarticle IDで重複排除して統合し、本文中の `[n]` 引用番号を新しい出典順へ付け替える。統合先はeditor-managedとし、統合元は削除規則に従って物理削除または削除済みマーカー化する。

### 整合性とバックアップ

分割・統合のDB変更は単一トランザクションで行う。削除・分割・統合の成功後は通常のユーザー管理Knowledge変更と同様にバックアップ予約を行う。

## Consequences

### Positive

- 不要な自動生成記事を削除しても再構築で復活しない。
- LLM Editorで編集済みの自動トピック記事を削除した場合も再生成を抑止できる。
- 長文記事をLLMの入力上限に依存せず分割できる。
- 分割・統合で既存本文を再生成しないため、意図しない内容変化を避けられる。
- 統合時も引用と出典の対応を維持できる。
- ユーザーの削除意思をバックアップ・復元後も保持できる。

### Negative

- 分割位置はH2見出しに限定される。適切な見出しがない記事は、先にLLM Editorで構造化する必要がある。
- 統合は構造的な連結であり、重複文章の要約や文章構成の再整理は自動では行わない。必要な場合は統合後にLLM Editorへ指示する。
- 削除済みマーカーは内部的にはknowledge_pagesに残るため、バックアップやDB診断では通常記事と区別して扱う必要がある。

## Relationship to existing ADRs

- ADR-0109: editor-managed記事を自動再構築から保護する方針を、手動削除の抑止にも利用する。
- ADR-0047: Knowledgeの永続化責務は`:feature:knowledge:data`に維持する。
- ADR-0056: LLM固有処理と決定論的な記事管理処理を分離する。
