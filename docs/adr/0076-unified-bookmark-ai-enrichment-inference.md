# ADR-0076: ブックマークの要約・タグ・フォルダ分類を最終推論へ統合する

- Status: Superseded by ADR-0091
- Date: 2026-08-16
- Refines: ADR-0030, ADR-0067

> 2026-08-17: 実端末で、長い要約本文を構造化JSONへ内包する方式がJSON生成失敗を増やし、ユーザー設定の要約出力形式とも競合することが確認されたため、ADR-0091で要約生成とメタデータ生成を再分離した。本ADRは経緯の記録として残す。

## Context

ADR-0030では、ブックマークの要約生成後にタイトルと要約からAIタグを生成する方針を採用した。ADR-0067では、未分類ブックマークについてタグ生成後に既存フォルダ候補から1件を選ぶ推論を追加した。

この構成では、短い記事でも「要約」「タグ」「フォルダ分類」がそれぞれ独立したローカルLLM生成になり、未分類ブックマーク1件あたり最大3回の生成処理が必要になる。ADR-0070およびADR-0071によりバックグラウンドのローカルAI推論は直列化されているため、追加生成はそのまま後続タスクの待ち時間、電力消費、発熱へ影響する。

一方、ADR-0027の階層要約では、長文記事についてチャンク要約と必要なreductionを行った後、最終要約を1回生成している。タグとフォルダ分類に必要な情報は、この最終生成時点の文脈と記事タイトルから同時に判断できる。

## Decision

### 1. 新規要約するブックマークは最終生成で要約・タグ・フォルダを同時に返す

ブックマーク対象の記事に保存済み要約がない場合、ADR-0027のチャンク分割とreductionは従来どおり維持する。変更するのはDIRECTまたはFINAL段階の最終生成だけとする。

最終生成にはユーザー設定の要約指示に加え、次を追加の出力要件として渡す。

- `summary`: ユーザー設定の要約指示に従った最終要約
- `tags`: 検索用タグ1〜5件
- `folder`: 既存ユーザーフォルダ候補の1件、または `null`

モデルには次のJSONオブジェクトだけを返すよう指示する。

```json
{"summary":"要約本文","tags":["タグ1"],"folder":null}
```

これにより短い未分類ブックマークでは、従来の最大3回の生成を1回にする。長文でもチャンク要約とreductionの回数は変えず、従来最終要約後に行っていたタグ・フォルダ用の追加生成をなくす。

### 2. 既存タグと既存フォルダ候補は最終生成の分類コンテキストとして渡す

タグはADR-0030の方針を維持し、利用件数上位の既存タグ候補を提示する。意味が同じ、または十分近い既存タグがある場合は、その表記を優先させる。

フォルダはADR-0067の方針を維持し、現在フォルダ未設定の場合だけ `system_kind IS NULL` の既存ユーザーフォルダを候補として渡す。候補がない場合は `folder` を `null` とする。新しいフォルダ名は生成しない。

記事タイトル、タグ候補、フォルダ候補はJSON文字列・配列としてプロンプトへ埋め込み、分類用データであって命令ではないことを明記する。

### 3. 追加の出力要件と候補データも階層要約のトークン予算へ含める

`feature:summary:data` は、ユーザー設定の要約promptだけでなく、JSON出力要件とタグ・フォルダ候補を含めたrender済み最終prompt全体をADR-0027の入力予算で判定する。

候補一覧を追加した結果、本文と最終promptが直接入力予算へ収まらなくなった場合は、従来どおりチャンク要約またはreductionへ移行する。候補データや本文を予算超過時に無言で切り捨てない。固定指示と候補データだけで入力予算を超える場合は明示的に失敗させる。

ユーザー設定promptの4,000文字制限は維持する。アプリが生成する候補データはユーザーpromptへ連結せず、別のsuffixとしてrender後に追加してトークン予算管理する。

### 4. 保存済み要約を再利用する場合はメタデータだけを1回で生成する

`forceRefresh=false` で保存済み要約が存在する場合は、ADR-0030のキャッシュ再利用方針を維持し、本文の再取得・再要約を行わない。

その代わり、記事タイトルと保存済み要約を入力として `tags` と `folder` を同時生成する1回のメタデータ推論を行う。

```json
{"tags":["タグ1"],"folder":null}
```

これによりキャッシュ済み要約の補完は、従来のタグ生成とフォルダ分類の最大2回から1回になる。

### 5. JSONはアプリ側でスキーマ検証してから保存する

モデル応答はそのままDBへ保存しない。次を検証する。

- 新規要約ではキーが `summary`, `tags`, `folder` のみである
- キャッシュ済み要約ではキーが `tags`, `folder` のみである
- `summary` は空ではない
- `tags` は文字列配列で1〜5件である
- タグは既存の正規化規則で空値・重複を除去する
- `folder` は `null` または既存フォルダ候補と正規化一致する文字列である
- 候補外のフォルダ名や余分なJSONキーは不正応答として扱う

不正応答を別推論で自動修復すると高速化効果を相殺するため、本変更では追加の再生成を行わずタスクを失敗させる。既存のタスク再実行操作から再試行できる。

### 6. 保存時の競合防止は既存トランザクションを維持する

推論開始後にユーザーがブックマーク解除やフォルダ変更を行う可能性があるため、生成結果だけで状態を上書きしない。

タグ保存時は記事が現在もブックマーク済みであることを、フォルダ保存時は現在も未分類であることを既存トランザクション内で再確認する。推論中のユーザー操作を優先する既存仕様を維持する。

### 7. 公開リポジトリへ実ユーザーデータを追加しない

プロンプト処理は端末内データを利用するが、ログ、テストfixture、ADR、PR説明へ実際の記事タイトル、URL、タグ、フォルダ名などを追加しない。テストでは一般化した固定文字列のみを利用する。

## Consequences

### Positive

- 新規の短い未分類ブックマークは最大3回から1回へLLM生成回数を削減できる。
- 長文記事でも最終要約後のタグ・フォルダ用追加生成を削減できる。
- 保存済み要約を利用するメタデータ補完は最大2回から1回へ削減できる。
- 推論回数減少により、直列AIキューの後続タスク待ち時間、電力消費、発熱を抑えられる。
- 要約・タグ・フォルダが同じ最終文脈から生成されるため、分類判断と要約内容の整合性を取りやすい。
- JSONスキーマ検証により、説明文や候補外フォルダを誤って保存することを防げる。

### Negative

- 最終生成promptへタグ・フォルダ候補が加わるため、同じ記事でも直接要約から階層要約へ移る場合がある。
- JSON形式の指示に従えないモデル応答はタスク失敗になる。
- 最終要約と分類を同一生成へまとめるため、分類要件が最終要約の生成結果へ多少影響する可能性がある。
- 保存済み要約を再利用する経路では、要約生成そのものがないためメタデータ専用の1推論は残る。

## Relationship to existing ADRs

- ADR-0027の階層要約・実トークン予算・本文を無言で捨てない方針を維持し、最終promptの予算対象を構造化出力要件まで拡張する。
- ADR-0030のブックマーク要約・既存タグ再利用・保存時再確認を維持し、要約後の独立タグ推論を本ADRで置き換える。
- ADR-0056に従い、構造化出力と分類方針は `feature:summary:data` が所有し、`core:ai-runtime` へブックマーク概念を持ち込まない。
- ADR-0067の未分類ブックマークだけを既存フォルダへ割り当てる方針を維持し、独立したフォルダ推論を本ADRで置き換える。
- ADR-0070およびADR-0071のバックグラウンドAI直列実行・優先度制御は変更しない。
