# ADR-0078: RSS記事へ階層的なコンテンツ種別を導入する

- Status: Accepted
- Date: 2026-08-16

## Context

RSSには通常の記事だけでなく、漫画サービスの更新や作品ページなど、本文要約を前提としないコンテンツも流入する。これまでArticle/Feed/FeedFolderにはコンテンツ種別がなく、ブックマーク追加や未要約ブックマークのバックフィルでは、YouTube/RedditのみURL・feed URLの個別判定で自動AI処理から除外していた。

漫画サービスを同様のURL例外として追加すると、サービス追加のたびに横断ポリシーが増え、RSSコンテンツ自身の意味とAI処理能力が分離できない。また、作品単位では同じフィード内でも例外設定が必要になる可能性があり、フィードだけに種別を持たせるのも不十分である。

一方、同一フォルダに漫画フィードをまとめる場合は、各フィードを個別設定するよりフォルダ単位の既定値を継承できる方が運用しやすい。

## Decision

### 1. `ContentType` をArticle domainの概念として導入する

初期のコンテンツ種別は次の2種類とする。

- `ARTICLE`: 通常の記事。自動AI enrichmentの対象になり得る。
- `COMIC`: 漫画・コミック。自動AI enrichmentの対象外とする。

コンテンツ種別はRSS固有のネットワーク形式ではなく、アプリが扱うArticleの意味を表すため `:feature:article:domain` が所有する。将来必要になった場合に動画・音声などを追加できるが、現時点では未使用の種別を先行追加しない。

### 2. 記事・RSSフィード・RSSフォルダの各階層にnullableな明示指定を持つ

DBには次のnullableなoverride値だけを保存する。

- `articles.content_type`
- `feeds.content_type`
- `feed_folders.content_type`

nullは「上位の設定を継承する」を意味する。実効値を各記事へ複製して保存しない。

### 3. 実効コンテンツ種別は記事 > フィード > フォルダ > ARTICLEの順に解決する

Articleの実効種別は次の優先順位で決定する。

1. 記事自身の明示指定
2. 所属RSSフィードの明示指定
3. 所属RSSフォルダの明示指定
4. 既定値 `ARTICLE`

これにより、漫画フォルダを一度設定すれば配下の未指定フィード・記事へ即座に反映され、特定フィードや特定記事だけを上書きできる。

実効値は読み取り時にJOINして解決する。フォルダ設定変更のたびに配下の記事を一括更新しない。

### 4. 継承元を削除する場合は意味が失われないよう明示値へ退避する

継承元そのものを削除した結果だけでコンテンツ種別が変化することは避ける。

- RSSフォルダ削除時、そのフォルダの明示種別を継承していたフィードには同じ種別を明示値として退避してからフォルダを削除する。
- RSSフィード削除時、保存済みで残る記事がフィード/フォルダの明示種別を継承していた場合は、その実効種別を記事の明示値へ退避してからfeed_idを外す。

フィードを別フォルダへ移動した場合は、新しい継承先へ切り替わることをユーザー操作の意図として扱い、退避しない。

### 5. 自動AI enrichmentは実効コンテンツ種別の能力を確認する

`COMIC` は次の自動処理から除外する。

- ブックマーク追加を起点とする自動要約・AI enrichment
- アプリ起動時の未要約ブックマークバックフィル

ユーザーが明示的に画面から要約を要求する操作は本ADRでは禁止しない。

ADR-0064のYouTube/Reddit URL判定は、専用feature由来コンテンツを識別する既存の安全策として当面維持する。したがって自動AI処理は「コンテンツ種別が許可する」かつ「YouTube/Reddit除外に該当しない」場合のみ実行する。

### 6. 設定は既存バックアップへ含める

バックアップ形式をversion 5へ更新し、記事・フィード・RSSフォルダの明示 `content_type` を保存・復元する。version 1〜4は従来どおり復元し、コンテンツ種別は未指定として扱う。

保存していないRSS記事自体は従来からバックアップ対象外であるため、記事単位overrideも保存済み記事のみバックアップされる。フィード/フォルダの設定はバックアップされるため、通常のRSS記事は再取得後も継承設定を復元できる。

### 7. 公開リポジトリへ実ユーザーデータを追加しない

コンテンツ種別判定は端末内DBのメタデータだけで行う。テスト・ADR・ログには実際に購読している漫画サービスのURL、作品名、フィードURLを含めず、一般化した固定データだけを使用する。

## Consequences

### Positive

- 漫画RSSに不要な自動要約・AIタスクが発生しなくなる。
- 漫画フィードをフォルダ単位でまとめて一括設定できる。
- フィード単位・記事単位の例外を自然に表現できる。
- 新しいコンテンツ種別をサービス別URL例外ではなくドメイン概念として拡張できる。
- 上位設定の変更は読み取り時に反映され、大量レコードの更新を必要としない。
- 親の削除でも保存済みコンテンツの意味が意図せず変化しない。

### Negative

- Article取得時にFeed/FeedFolderとのJOINが追加される。
- 同じArticleモデルを生成する独自SQLは、同じ解決規則を適用する必要がある。
- フィード移動によって継承先が変わるため、移動後の実効種別も変わり得る。
- 保存していない記事の個別overrideは、アプリ再インストール時のバックアップ復元対象にはならない。

## Relationship to existing ADRs

- ADR-0003: Articleというアプリ固有概念をfeature側に置き、RSS domainからArticle domainへのdomain依存で共有する。
- ADR-0030: ブックマーク自動AI enrichmentの基本方針を維持し、対象可否へコンテンツ種別を追加する。
- ADR-0064: YouTube/RedditのURLベース除外は維持し、本ADRのコンテンツ種別判定とAND条件で適用する。
- ADR-0067: 未要約ブックマークのバックフィルでも同じ実効コンテンツ種別を使い、COMICを投入しない。
