# ADR-0025: 統合ビューを未処理・保留アイテムのホーム画面とする

- Status: Accepted
- Date: 2026-08-11
- Updated: 2026-08-12

## Context

Yomitori には RSS、Reddit、YouTube、メールなど、未読を順番に処理して一覧から減らしていく機能が複数ある。

それぞれの機能には専用画面があり、RSS・Reddit・メールの「あとで読む」、YouTube の「あとで見る」、メールの「スター」「アーカイブ」のように、未読から次の状態へ振り分ける操作も存在する。

一方、アプリを開いた時点では RSS、YouTube、メールなどを個別に巡回しなければ未処理件数の全体像が分からない。日常的に Inbox Zero を行う用途では、サービス単位で画面を切り替えることよりも「まだ判断していないものを一つのキューから減らす」ことが主目的になる。

さらに、一度「あとで読む」「あとで見る」へ保留した項目もサービスごとに巡回すると見落としやすい。未読の仕分けと、保留した項目の消化を同じ入口から行えるようにする。

ADR-0008 ではメールを未読キュー中心のトリアージ UI として扱い、メールの「あとで読む」を Gmail のスターとは独立した Yomitori 所有状態として保存することを決めている。ADR-0015 では RSS・メール・YouTube 等で距離ベースのスワイプ操作を共通化している。この操作モデルを機能横断の入口にも適用する。

## Decision

### 1. 「統合ビュー」をアプリのホーム画面にする

`MainTab.INTEGRATED` と `AppSection.HOME` を利用し、アプリ起動時の初期画面を統合ビューとする。

ナビゲーションドロワーの先頭にも「統合ビュー」を配置する。RSS、Reddit、YouTube、メールなどの専用画面は従来どおり残し、詳細な閲覧、検索、設定、履歴確認は各専用画面で行う。

### 2. 統合ビューは「未読」と「あとで読む」の2つのキューを持つ

統合ビュー内に「未読 / あとで読む」のボトムタブを設ける。

「未読」タブの対象は次の4種類とする。

- RSS: 未読記事
- Reddit: 未読投稿・コメント更新
- YouTube: 未読動画
- メール: 受信トレイ内の未読スレッド

「あとで読む」タブでは、未読タブから保留先へ振り分けた状態を横断表示する。

- RSS: あとで読む記事
- Reddit: あとで読む投稿・コメント更新
- YouTube: あとで見る動画
- メール: Yomitori のあとで読む状態にあるスレッド

メールの Gmail スターは「あとで読む」の抽出条件にしない。Gmail のスターと Yomitori のあとで読むは別の状態だからである。

既読履歴、ブックマーク全体、YouTube の保存済み、メールのスター一覧・アーカイブ一覧は統合ビューへ混在させない。それらは保留キューとは異なるため、各専用画面で扱う。

統合ビューでは各アイテムを共通の表示モデルへ射影し、元データや永続化モデルを共通化しない。「未読」は更新日時の降順、「あとで読む」は古い項目から消化しやすいよう更新日時の昇順で表示する。

両方のタブでサービス別に件数を確認しやすくするため、「すべて / RSS / Reddit / YouTube / メール」のフィルタを設ける。

### 3. 既存 ViewModel を統合ビューでも共有する

統合ビュー専用の横断 Repository や新しい共通 DB テーブルは作らない。

RSS、Reddit、YouTube、メールそれぞれの既存 ViewModel が持つ状態を UI 層で共通表示モデルへ変換し、状態変更も既存 ViewModel の操作へ委譲する。

これにより、統合ビューで処理した直後に個別画面へ移動しても同じ ViewModel 状態が利用され、別々のキャッシュや同期ロジックを二重に持たない。

YouTube の ViewModel は Compose の Activity スコープで取得し、統合ビューと YouTube 専用画面から同じインスタンスを参照する。

メールは統合ビューの選択タブに合わせて既存の mailbox を切り替える。「未読」では `Mailbox.UNREAD`、「あとで読む」では `Mailbox.READ_LATER` を選択し、ADR-0008 で定義した状態 semantics をそのまま利用する。

### 4. スワイプ操作を「処理済み」「保留」「保留解除」に正規化する

「未読」タブの基本操作は次のとおりとする。

- 左スワイプ: 既読 / 処理済みにする
- 右スワイプ: 後で処理する場所へ振り分ける
- メールのみ深い右スワイプ: アーカイブする

右スワイプの具体的な処理はソースごとに異なる。

- RSS: あとで読む
- Reddit: あとで読む
- YouTube: あとで見る
- メール: Yomitori 独自のあとで読む状態を設定し、未読なら既読にする

メールのあとで読む状態は ADR-0008 の `read_later_locally` が所有し、Gmail の `STARRED` やユーザーラベルへ変換しない。すでにあとで読む状態の未読メールを統合ビューから再度保留した場合も、あとで読む状態を維持したまま既読化する。

「あとで読む」タブでは左スワイプで各ソースの保留状態を解除する。

- RSS / Reddit: あとで読むを解除し、ブックマーク自体は未分類として残す
- YouTube: あとで見るを解除する
- メール: Yomitori のあとで読む状態を解除する。Gmail スターは変更しない

カードの退場アニメーションとスワイプ距離は ADR-0015 の `SwipeActionListItem` を再利用する。

### 5. 更新操作は各機能の既存更新処理を同時に開始する

統合ビューの pull-to-refresh は選択中のタブにかかわらず次をまとめて開始する。

- RSS フィード更新
- Reddit 更新
- YouTube 更新
- Gmail 同期

統合ビュー自身はネットワーク取得や永続化を実装せず、各機能の既存更新処理を呼び出す。

## Consequences

### Positive

- アプリを開いた直後に、サービスを横断した未処理件数と優先順を確認できる
- Inbox Zero の作業を一つの時系列キューで進められる
- 一度保留した項目も統合ビューから横断して消化でき、サービスごとの「あとで読む」巡回が不要になる
- Gmail スターを Yomitori の保留状態として流用せず、メール側の意味を保ったまま統合できる
- 既存の状態管理と同期処理を再利用するため、統合ビューと個別画面の状態乖離を抑えられる
- 新しい横断データベースや Repository を導入せず、既存 feature の境界を維持できる

### Negative

- 各 feature の UI state に統合ビューが依存するため、対象 feature の表示モデル変更時には統合ビュー側も追随が必要になる
- 「あとで読む」は各機能で意味が完全には同一ではなく、解除後の状態も各 feature の既存仕様に従う
- ブックマーク全体、保存済み、スター、アーカイブ、履歴を横断検索する画面ではない
- 更新処理は各 feature の非同期処理を開始する方式なので、完了タイミングはソースごとに異なる
- メール画面の選択 mailbox は統合ビューのタブ切り替えに応じて未読またはあとで読むへ変更される

## Relationship to existing ADRs

- ADR-0001 の UI / Domain / Data の責務分離を維持し、統合ビューは既存 Domain/Data の所有権を奪わない
- ADR-0003 / ADR-0004 の feature 境界を維持し、feature 同士を直接依存させない
- ADR-0008 のメール未読キューと Yomitori 独自のあとで読む状態へ操作を委譲し、Gmail スターとは分離する
- ADR-0009 の Reddit 専用 feature 分離を維持し、統合ビューでは表示だけを集約する
- ADR-0010 の YouTube 専用 feature 分離を維持し、購読・あとで見る・保存状態は YouTube feature が所有する
- ADR-0015 の共通スワイプ UI primitive を統合ビューでも利用する
- ADR-0019 の feature 内ボトムタブ方針を統合ビューにも適用し、「未読 / あとで読む」を画面下部で切り替える
