# ADR-0025: 統合ビューを未処理アイテムのホーム画面とする

- Status: Accepted
- Date: 2026-08-11

## Context

Yomitori には RSS、Reddit、YouTube、メールなど、未読を順番に処理して一覧から減らしていく機能が複数ある。

それぞれの機能には専用画面があり、RSS の「あとで読む」、Reddit の「保存」、YouTube の「あとで見る」、メールの「スター」「アーカイブ」のように、未読から次の状態へ振り分ける操作もすでに存在する。

一方、アプリを開いた時点では RSS、YouTube、メールなどを個別に巡回しなければ未処理件数の全体像が分からない。日常的に Inbox Zero を行う用途では、サービス単位で画面を切り替えることよりも「まだ判断していないものを一つのキューから減らす」ことが主目的になる。

ADR-0008 ではメールを未読キュー中心のトリアージ UI として扱うことを決めており、ADR-0015 では RSS・メール・YouTube 等で距離ベースのスワイプ操作を共通化している。この操作モデルを機能横断の入口にも適用する。

## Decision

### 1. 「統合ビュー」をアプリのホーム画面にする

`MainTab.INTEGRATED` と `AppSection.HOME` を追加し、アプリ起動時の初期画面を統合ビューとする。

ナビゲーションドロワーの先頭にも「統合ビュー」を配置する。RSS、Reddit、YouTube、メールなどの専用画面は従来どおり残し、詳細な閲覧、検索、設定、履歴確認は各専用画面で行う。

### 2. 統合ビューは「未処理キュー」を集約する

初期対象は次の4種類とする。

- RSS: 未読記事
- Reddit: 未読投稿・コメント更新
- YouTube: 未読動画
- メール: 受信トレイ内の未読スレッド

既読履歴、RSS の「あとで読む」、YouTube の「あとで見る」、メールのスター・アーカイブ一覧そのものは統合ビューへ混在させない。それらは「仕分け後の行き先」であり、Inbox Zero の処理対象とは別だからである。

統合ビューでは各アイテムを共通の表示モデルへ射影し、更新日時の降順で混在表示する。元データや永続化モデルを共通化しない。

サービス別に件数を確認しやすくするため、「すべて / RSS / Reddit / YouTube / メール」のフィルタを設ける。

### 3. 既存 ViewModel を統合ビューでも共有する

統合ビュー専用の横断 Repository や新しい共通 DB テーブルは作らない。

RSS、Reddit、YouTube、メールそれぞれの既存 ViewModel が持つ状態を UI 層で共通表示モデルへ変換し、状態変更も既存 ViewModel の操作へ委譲する。

これにより、統合ビューで処理した直後に個別画面へ移動しても同じ ViewModel 状態が利用され、別々のキャッシュや同期ロジックを二重に持たない。

YouTube の ViewModel は Compose の Activity スコープで取得し、統合ビューと YouTube 専用画面から同じインスタンスを参照する。

メールは統合ビューへ入った時に `Mailbox.UNREAD` を選択し、ADR-0008 で定義した「受信トレイ内の未読」という処理キューと操作 semantics をそのまま利用する。

### 4. スワイプ操作を「処理済み」と「保留」に正規化する

統合ビューの基本操作は次のとおりとする。

- 左スワイプ: 既読 / 処理済みにする
- 右スワイプ: 後で処理する場所へ振り分ける
- メールのみ深い右スワイプ: アーカイブする

右スワイプの具体的な処理はソースごとに異なる。

- RSS: あとで読む
- Reddit: 保存して既読
- YouTube: あとで見る
- メール: スターを維持または付与して既読

メールがすでにスター済みの場合、右スワイプでスターを解除せず既読だけにする。統合ビューの右スワイプは「保留先へ残して未読キューから完了させる」操作だからである。

カードの退場アニメーションとスワイプ距離は ADR-0015 の `SwipeActionListItem` を再利用する。

### 5. 更新操作は各機能の既存更新処理を同時に開始する

統合ビューの pull-to-refresh は次をまとめて開始する。

- RSS フィード更新
- Reddit 更新
- YouTube 更新
- Gmail 同期

統合ビュー自身はネットワーク取得や永続化を実装せず、各機能の既存更新処理を呼び出す。

## Consequences

### Positive

- アプリを開いた直後に、サービスを横断した未処理件数と優先順を確認できる
- Inbox Zero の作業を一つの時系列キューで進められる
- 既存の状態管理と同期処理を再利用するため、統合ビューと個別画面の状態乖離を抑えられる
- 新しいデータベースや横断 Repository を導入せず、既存 feature の境界を維持できる
- 今後、同じ「未処理キュー」を持つ機能を共通表示モデルへ追加しやすい

### Negative

- 各 feature の UI state に統合ビューが依存するため、対象 feature の表示モデル変更時には統合ビュー側も追随が必要になる
- 「あとで読む」「スター」「アーカイブ」など仕分け後の全アイテムを統合検索する画面ではない
- 更新処理は各 feature の非同期処理を開始する方式なので、完了タイミングはソースごとに異なる
- メール画面の選択 mailbox は統合ビューへ入ると未読へ戻る

## Relationship to existing ADRs

- ADR-0001 の UI / Domain / Data の責務分離を維持し、統合ビューは既存 Domain/Data の所有権を奪わない
- ADR-0003 / ADR-0004 の feature 境界を維持し、feature 同士を直接依存させない
- ADR-0008 のメール未読キュー、スター、アーカイブの意味をそのまま利用する
- ADR-0009 の Reddit 専用 feature 分離を維持し、統合ビューでは表示だけを集約する
- ADR-0010 の YouTube 専用 feature 分離を維持し、購読・保存状態は YouTube feature が所有する
- ADR-0015 の共通スワイプ UI primitive を統合ビューでも利用する
- ADR-0019 の feature 内ボトムタブ方針は変更せず、統合ビューはアプリ全体の入口として追加する
