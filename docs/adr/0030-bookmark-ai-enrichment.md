# ADR-0030: ブックマーク追加時にAIメタデータを自動生成する

- Status: Accepted
- Date: 2026-08-13
- Supersedes: ADR-0051 (RSS read-later auto summary)

## Context

ブックマークはRSS、Reddit、共有インテント、ホーム画面ウィジェットなど複数の入口から追加される。従来はRSSの「あとで読む」だけが任意設定によって要約キューへ投入され、タグ付けは手動だった。またAIチャットのブックマーク検索はタイトル、配信元、フォルダ、タグのみを参照し、保存済み要約を検索や回答へ利用していなかった。

ブックマークを後から検索・再利用する用途では、保存時点で要約とタグが揃っている方が有用である。さらに、すでに生成済みの要約がある記事をブックマークした場合に同じ本文を再取得して再要約する必要はない。

一方、Bookmark feature がAI runtimeやSummary dataへ直接依存すると feature 境界が崩れる。ADR-0003では `:app` を composition root とし、feature 間の連携をそこで組み立てる方針としている。ADR-0005ではAIチャットがSkill経由でアプリ内リソースを読み取る方針を採用している。

## Decision

### 1. 対話的なブックマーク追加をAI処理の起点にする

RSS、Reddit、共有インテント、ホーム画面ウィジェットなど、通常の操作によって新しくブックマーク状態になった記事は、自動的にAIメタデータ処理を要求する。

ブックマーク保存自体とAI処理は異なる成功条件とする。AIキュー投入や生成に失敗してもブックマークを巻き戻さない。

CSV/HTMLの一括インポートはこの自動処理の対象外とする。一括復元で大量のAIタスクが予期せず生成されることを避け、通常のユーザー操作による追加と明確に分ける。

### 2. Bookmark feature はAI featureに依存しない

`DefaultBookmarkRepository` は、新規ブックマーク成立後に呼ぶ汎用の suspend callback を受け取る。Bookmark側はcallbackの意味を知らず、AI型やSummary型を参照しない。

`:app` の `AppContainer` がcallbackを `SummaryRepository.requestBookmarkEnrichment(articleId)` へ接続する。これにより、複数画面からの保存処理をBookmarkRepositoryへ集約したまま、AI処理をcomposition rootで組み合わせる。

ホーム画面ウィジェットの「あとで読む」も直接SQL更新を行わず、BookmarkRepositoryを経由させる。

### 3. 既存のSummaryキューを要約とタグ付けの処理単位として再利用する

新しい永続キューやDBテーブルは追加しない。既存のSummary WorkManagerキューで、次の順に処理する。

1. 保存済み要約があり `forceRefresh=false` なら、その要約をそのまま再利用する。
2. 要約がなければ記事本文を取得し、既存の階層要約処理で要約を生成・保存する。
3. 処理対象が現在ブックマークされていれば、タイトルと要約を入力として1〜5件の検索用タグを生成する。
4. タグ生成前に既存タグを利用件数の多い順で最大100件取得し、候補一覧としてAIプロンプトへ渡す。意味が同じ、または十分近い既存タグがある場合は、その既存タグ名を同じ表記で優先して返し、既存タグで表現できない概念だけ新しいタグを生成するよう指示する。
5. 既存タグ候補はユーザーデータとして扱い、候補内の文字列をAIへの指示として解釈しない旨をプロンプトへ明記する。
6. タグ保存トランザクション内で記事が現在もブックマーク済みか再確認し、保存解除済みならタグを書き込まない。
7. 既存タグを置換せず、正規化名で重複排除して追加する。AIが既存タグ名を返した場合は既存の `tags` レコードを再利用する。
8. タグ関係が実際に追加された場合は、アプリとバックグラウンドWorkerで共有する `DataChangeNotifier` を更新し、開いているBookmark画面にも変更を反映する。
9. タグ生成が空または失敗ならタスクを failed とし、保存済み要約は保持して再実行時に再利用する。

明示的な `forceRefresh=true` の要約要求は従来どおり要約を再生成する。対象記事がブックマーク済みなら、その後のAIタグ生成も実行する。

ADR-0029で追加した要約タスクの進捗永続化と30日ログ保持は維持する。

### 4. 自動タグと手動タグは同じタグ体系へ追加し、対象を失ったタグは削除する

今回、新たなタグ種別やprovenance列は導入しない。AI生成タグは既存の `tags` / `article_tags` を利用し、手動タグと同じ正規化規則で重複排除する。

AI処理は現在関連付けられている既存タグを置換しないため、ユーザーが手動で整理したタグを生成処理だけで削除しない。

一方、`article_tags` の最後の関連が削除され、どの記事からも参照されなくなったタグは `tags` から自動削除する。SQLiteの `AFTER DELETE` triggerを利用し、ブックマーク解除、タグ手動解除、記事削除に伴う外部キーCASCADEのいずれでも同じ不変条件を保つ。

既存DBをこの設計へ移行する際は、すでに存在する参照なしタグを一度削除する。AIタグと手動タグの出自を区別しない設計のため、この整理もタグの出自に関係なく適用する。

タグ編集で選択中のタグを一時的に削除してtriggerに消されることを避けるため、記事とタグの関連更新は全削除・再追加ではなく、現在値との差分だけを削除・追加する。

### 5. AIチャットは保存済み要約とタグをブックマーク検索・回答に利用する

`bookmark-reader` SkillへSummaryの読み取り契約を渡す。保存済み記事と「あとで読む」の検索対象にタイトル、配信元、フォルダ、タグ、保存済みAI要約を含める。

Toolの返却結果にもタグと要約を含め、チャットモデルが記事内容に関する質問へ保存済み情報から回答できるようにする。要約データはSummary featureを正本とし、Bookmarkモデルへ複製しない。

### 6. 旧RSS専用設定を廃止する

RSSの「あとで読む」だけをopt-inで自動要約する旧設計は本ADRで廃止する。設定画面のトグルも削除し、ブックマーク追加時のAI処理は通常動作とする。

## Consequences

### Positive

- ブックマークの入口に依存せず、保存後の要約・タグ付けが一貫する。
- 既存要約がある記事では本文取得と再要約を省略できる。
- 既存タグをAIへ提示することで、意味の近いタグが増殖しにくくなり、既存の分類体系を再利用しやすい。
- 対象記事を失ったタグが自動整理され、タグ一覧に利用先のないAI生成タグが残り続けない。
- AIチャットがタイトルだけでなく、要約本文やタグを使って保存情報を検索できる。
- Bookmark feature とAI runtimeの依存を分離できる。
- 手動タグを壊さずAIタグを補助情報として追加できる。
- タグ生成中に保存解除された記事へAIタグが復活する競合を防げる。
- バックグラウンドでタグ生成が完了しても、開いているBookmark画面が変更通知で更新される。

### Negative

- ブックマーク追加ごとにローカルAIタスクが発生するため、端末負荷は従来より増える。
- モデル未選択時はAIタスクがfailedになり、モデル準備後に再実行が必要になる。
- AI生成タグと手動タグの出自はDB上で区別できない。
- 一度記事へ関連付けたタグは最後の対象を失うと削除されるため、対象がない状態で将来用の分類語として保持する用途には使えない。
- AIへ渡す既存タグ候補はプロンプト長を抑えるため利用件数上位100件に制限され、それ以外の既存タグは生成時に直接参照されない。
- チャット検索時は各ブックマークに対応する保存済み要約を参照するため、ブックマーク件数に応じてローカルDB読み取りが増える。
- 一括インポートしたブックマークは自動AI処理されない。
- バックグラウンドWorkerから画面更新を伝えるため、アプリプロセス内で共有する変更通知インスタンスを利用する。

## Relationship to existing ADRs

- ADR-0003のcomposition rootとfeature境界の方針に従う。
- ADR-0005のAgent Skill方式を拡張し、bookmark-readerへSummaryの読み取り情報を追加する。
- RSS固有のopt-in自動要約を本ADRで置き換える。
- ADR-0027の階層要約を、要約未生成時の生成経路として引き続き利用する。
- ADR-0029の要約進捗永続化とジョブログ保持方針を維持する。
